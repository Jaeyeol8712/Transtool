## 2. 전문 지식 체계 (10년차가 아는 것)

### 2-1. GA4 데이터 모델
- **이벤트 + 매개변수 모델** → 모든 것이 이벤트다. 페이지뷰도 `page_view` 이벤트. 사용자·세션은 이벤트에 붙은 식별자로 묶어 계산한다 → 기준: 지표를 말할 때 "이벤트 수 / 사용자 수 / 세션 수" 중 무엇인지 항상 붙인다.
- **범위(scope)를 섞지 않는다** → `sessionSourceMedium`(세션 범위)과 `firstUserSource`(사용자 첫 유입)는 다른 질문에 대한 답이다. 우리 보고서의 "버튼 누른 사람은 어디서 왔나"는 `sessionDefaultChannelGroup`·`sessionSourceMedium` 기준이므로 정확히는 "버튼을 누른 그 방문(세션)의 유입"이다. 첫 방문 경로를 묻는다면 `firstUser*` 차원을 써야 한다.
- **사용자 수는 더할 수 없다** → `totalUsers`는 고유 수라서 행(채널·글·날짜)별 값을 합치면 같은 사람이 여러 행에 있을 때 과대 계산된다. 합계가 필요하면 차원 없이 다시 조회해야 한다. 기준: 합계 사용자 = 별도 쿼리 값, 행 합산 금지.
- **맞춤 매개변수는 등록해야 보고서에 나온다** → 이벤트에 붙여 보낸 매개변수(예: `post_slug`, `button_position`, `entry_source`, `entry_page`)는 GA4 관리 화면에서 맞춤 측정기준으로 등록해야 API·탐색에서 쓸 수 있다. 등록 전 데이터는 소급되지 않는다.
- **`search_term` 매개변수의 이중 의미** → GA4의 기본 측정기준 '검색어(searchTerm)'는 `search_term` 매개변수에서 채워진다. 사이트 내 검색(`view_search_results`)도 같은 이름을 쓰므로, 우리처럼 `cta_click`에 외부 검색어를 실어 보낼 때는 반드시 이벤트 이름으로 필터해야 섞이지 않는다(현재 스크립트는 `eventName = cta_click` 필터를 걸어 안전).
- **처리 지연** → GA4 표준 보고서·Data API 숫자는 처리 완료까지 시간이 걸리며, 전날 데이터가 아침에 완전하지 않을 수 있다. 기준: 일간 보고서의 "어제" 숫자는 잠정치로 표기하고, 다음 날 보고서에서 그제 숫자를 한 번 더 확정치로 보여 준다. (정확한 지연 시간은 속성 규모에 따라 다름 — 확인 필요)
- **(other) 행과 기준점(thresholding)** → 고유값이 매우 많은 차원은 (other)로 묶일 수 있고, Google 신호 데이터가 켜져 있으면 작은 숫자가 숨겨질 수 있다. 기준: 이상하게 0이 나오면 Google 신호 설정과 기간을 먼저 확인.

### 2-2. 탐색(Explorations)과 기여(Attribution)
- **유입경로 탐색(퍼널)** → 단계별 이탈을 본다. 우리 퍼널: 계산기·맛집·가이드 진입 → 추천 카드(`promo-*`)·목록(`hub-*`) 클릭 → 추천 글(`/shop-*`) 조회 → BC 버튼(`cta-*`) 클릭. 기준: "개방형(open)" 퍼널로 중간 진입을 허용해야 검색으로 추천 글에 바로 들어온 사람도 셀 수 있다.
- **경로 탐색** → 추천 글 직전 페이지를 본다. 카드가 실제로 글을 보내 주는지 확인하는 용도.
- **기여 모델** → GA4는 데이터 기반 기여와 마지막 클릭 등 일부 모델만 남겼다. 우리 수익 이벤트(`cta_click`)는 대부분 같은 세션 안에서 일어나므로 세션 범위 마지막 비직접 클릭 기준으로 충분하다. 여러 날에 걸친 재방문 비중이 커지면 `firstUser*`와 비교.
- **직접(Direct)의 함정** → 앱 내 브라우저(카카오톡·인스타그램)·북마크·리퍼러 차단은 Direct로 잡힌다. 카페·인스타 링크에는 UTM을 붙여야 채널이 보존된다. 기준: 우리가 직접 뿌리는 모든 링크에 `utm_source`·`utm_medium`·`utm_campaign`.

### 2-3. 서치 콘솔(구글)·서치어드바이저(네이버)
- **지연** → 서치 콘솔 실적 데이터는 2~3일 늦다(우리 스크립트도 `today-3`일까지만 조회). 일간 보고서의 구글 검색어는 "3일 전까지" 숫자임을 명시.
- **익명화 검색어** → 개인정보 보호로 드물게 검색된 검색어는 query 차원 조회에서 빠진다. 그래서 query+page 합계는 page만의 합계보다 작다. 기준: 페이지별 클릭 합계는 page 차원만으로 따로 조회.
- **행 제한** → API는 요청당 rowLimit을 지정한다. 현재 `gsc()`는 query×page 100행만 가져온다. 글 17개 × 검색어 다수면 잘린다. 기준: 1,000행 이상 + 페이지네이션(startRow).
- **평균 순위** → 노출 가중 평균이라, 노출이 적은 검색어는 순위가 크게 흔들린다. 노출 100 미만의 순위 변화는 보고하지 않는다.
- **브랜드 검색어 필터** → 2026년 서치 콘솔에 브랜드 검색어 필터가 확대 적용됐다는 보도가 있다 [5]. "어라운드툴"·"aroundtool" 검색과 일반 검색을 나눠 보는 데 쓴다(우리 속성에 적용됐는지 확인 필요).
- **네이버** → 네이버 검색은 리퍼러에 검색어(query)를 남기지 않는 경우가 많아 GA4에선 '(검색어 미전달)'이 많다. 전체 검색어는 서치어드바이저 리포트에서 봐야 한다. API 연동은 없으므로 주 1회 수동 기록(확인 필요: 서치어드바이저 데이터 내려받기 범위).

### 2-4. 중복·봇·내부 방문 걸러내기
- **GA4의 알려진 봇 제외** → GA4는 알려진 봇·스파이더 트래픽을 자동 제외하며 끌 수 없고, 제외된 양을 보여 주지도 않는다. 그래서 남은 이상 트래픽은 직접 찾아야 한다 [3].
- **이상 징후 판별 기준(경험칙)** → ① 참여 시간 0초에 가까운 세션이 특정 날짜·도시·소스에 몰림 ② 같은 페이지 반복 조회가 비정상적으로 많음 ③ 화면 해상도·브라우저가 한 종류로 쏠림 ④ 리퍼러가 처음 보는 도메인. 하나라도 보이면 해당 세그먼트를 빼고 다시 계산해 두 숫자를 함께 보고한다.
- **내부 트래픽** → GA4 관리 → 데이터 스트림 → 태그 설정 → 내부 트래픽 정의(IP)로 대표·팀 방문을 표시하고, 데이터 필터를 '테스트'로 먼저 돌려 본 뒤 '활성'으로. 대표 IP는 저장소에 남기지 않는다.
- **중복(같은 사람의 반복)** → 우리 보고서는 "횟수 − 사람 수"를 중복으로 표시한다(결정기록: 중복 별도 표시). 사람 = 같은 기기·브라우저. 같은 사람이 휴대폰과 PC로 오면 2명으로 센다는 한계를 매 보고서 각주로 유지.
- **호스트 확인** → 측정 ID가 다른 도메인(예: 복제 사이트, 로컬 미리보기)에서 실행되면 숫자가 섞인다. 기준: 주 1회 `hostName` 차원으로 aroundtool.com 외 호스트 확인. 퍼가기(embed) 페이지에는 GA 태그가 없어 외부 사이트 이용은 측정되지 않는다(확인함: `embed/*.html` 에 측정 ID 없음).

### 2-5. 작은 표본 해석
- **퍼센트 변화 금지 구간** → 클릭 2→3은 +50%지만 의미 없다. 기준(경험칙): 비교하는 두 값 중 하나라도 20 미만이면 % 대신 "2회 → 3회"처럼 절대값만 쓴다.
- **포아송 변동** → 하루 클릭 수처럼 드문 사건의 횟수는 평균 λ일 때 표준편차가 √λ 정도다. 평균 4회면 ±2회(약 0~8회)는 그냥 흔들림이다. 기준: 최근 7일 평균 ±2√평균 밖일 때만 "이상"으로 보고.
- **비율의 신뢰구간** → 클릭률처럼 n이 작은 비율은 Wilson 구간을 쓴다. 예: 조회 50, 클릭 3(6%)의 95% 구간은 대략 2~16%로 넓다. 기준: 구간이 겹치면 "차이 없음"으로 보고.
- **기간 묶기** → 일간이 흔들리면 주간·4주 누적으로 판단한다. 우리 보고서가 일간에도 최근 3일·7일을 함께 보여 주는 이유.
- **생존자 편향** → 클릭 상위 글만 보면 노출이 적은 신규 글을 과소평가한다. 글 나이(게시 후 일수)를 함께 본다.

### 2-6. A/B 테스트
- **트래픽이 작을 때의 현실** → 기준 클릭률 3%에서 상대 30% 향상(3%→3.9%)을 80% 검정력·유의수준 5%로 잡으려면 그룹당 수천~1만 회 조회 수준이 필요하다(표본 크기 계산기로 계산, 정확한 값은 기준율에 따라 다름). 추천 글 조회가 하루 수십 회 수준이면 수개월이 걸린다.
- 그래서 우리 규칙: ① 한 번에 하나만 바꾼다 ② 사전에 기간·지표·판정 기준을 적는다 ③ 기간 중간에 엿보고 멈추지 않는다 ④ 결론이 "차이 확인 불가"여도 기록한다 ⑤ 큰 차이를 기대할 수 있는 변경(버튼 위치·문구)만 실험한다.
- **배정 방법** → 정적 사이트(GitHub Pages)라 서버 배정이 없다. 브라우저에서 무작위 배정하고 `localStorage`에 고정, GA4 이벤트에 `variant` 매개변수를 실어 보내는 방식이 현실적(맞춤 측정기준 등록 필요).
- **전후 비교의 한계** → 날짜로 나눈 전후 비교는 요일·시즌·검색 순위 변동이 섞인다. 불가피하면 같은 요일 구성의 2주 대 2주로 비교하고 "인과 아님"을 명시.
- **결정기록과의 관계** → 깜빡임 제거는 대표 확인 대기 중이므로 실험 설계안만 준비하고 집행하지 않는다.

### 2-7. 보고서 시각화
- 막대는 0에서 시작, 비교 대상은 같은 축. 우리 `columns()` 는 0 기준 축과 사람 수+중복 쌓기 막대를 쓴다(원칙 부합).
- 색은 의미가 하나: 조회=파랑(`--s1`), 클릭=주황(`--s2`). 빨강·초록은 증감에만.
- 표에는 단위·기간·기준(사람/횟수)을 머리글에 쓴다. 작은 표본 경고는 숫자 옆에 직접.
- 결정기록: 그래프·표 중심, 최근 3일 포함, 중복 별도 표시. 문장 요약은 3줄 이내.

| 카드·목록이 보낸 클릭 | linkId | eventCount | linkId BEGINS_WITH hub- 또는 promo- |
| 팝업 성과 | customEvent:post(등록 후) | eventCount | eventName IN popup_view, popup_click |
| 호스트 점검 | hostName | screenPageViews | 없음 |
| 봇 의심 | sessionSource, city, deviceCategory | sessions, userEngagementDuration | 참여시간/세션 이 0에 가까운 행 정렬 |
| 광고 세션 | sessionSourceMedium, sessionManualAdContent | sessions, eventCount | sessionMedium IN cpc, paid_social |

- 비교 기간은 같은 요일 수로 맞춘다(일간: 어제 vs 지난주 같은 요일도 함께).
- 쿼리 실패는 숫자 0이 아니라 "불러오지 못함"으로 표시한다(현재 `ERRORS` 처리 유지).
- Data API는 속성당 시간·일 단위 토큰 할당량이 있다. 보고서 종류가 겹치는 날(1월 3일: 일간+월간+분기+연간)은 쿼리 수가 많아지므로 429 재시도 로그를 확인한다(할당량 수치는 확인 필요).

### 2-9. 정의 사전 (보고서에 쓰는 말)
- 조회수: `/shop-` 페이지 `screenPageViews`. 본 사람: 같은 범위 `totalUsers`.
- BC 버튼 클릭: `cta_click` 중 `cta-` 로 시작하는 `link_id`(top·mid·end·pop). 목록(`hub-`)·카드(`promo-`)는 '글로 들어온 클릭'이지 수익 클릭이 아님.
- 클릭률: 클릭 ÷ 조회수. 사람 기준 클릭률: 누른 사람 ÷ 본 사람.
- 중복: 횟수 − 사람 수. 같은 사람이 다른 기기로 오면 중복이 아니라 2명.
- 검색어 미전달: 외부 리퍼러는 있으나 검색어가 없는 경우. 직접·내부: 리퍼러 없음 또는 사이트 내부.

## 3. 어라운드툴에 적용하면

### 현재 보고 체계 (확인한 것)
- `.github/workflows/cta-report.yml`: 매일 UTC 23:13(= KST 08:13) 실행, Workload Identity 또는 서비스 계정으로 인증, `scripts/ga4-report.mjs` 실행, 결과를 `cta-report` 브랜치 `reports/*.html`, `today.json`, `cta-latest.md` 로 커밋.
- 자동 판단: 일간 매일, 주간 수요일(지난 월~일), 월간 3일, 분기 1·4·7·10월 3일, 연간 1월 3일 — 결정기록과 일치.
- GA4 Data API `runReport` 8~9종 쿼리를 순차 실행(429면 재시도). 서치 콘솔은 `/shop-` 포함 페이지의 query×page 100행.
- `site.js`: `cta_click` 에 `link_id`·`post_slug`·`button_position`·`cta_type`·`search_term`(외부 검색어 또는 '(검색어 미전달)'·'(직접·내부)')·`entry_source`·`entry_page` 를 실어 보낸다. 첫 유입 정보는 `sessionStorage('at_entry')` 에 탭 단위로 저장.
- 팝업 노출·클릭은 `popup_view`·`popup_click` 이벤트로 따로 들어온다(보고서에는 아직 미사용).
- `ga4-visitors.mjs`: 매시간 오늘·어제·전체 활성 사용자 → `assets/visitors.json`.

### 잘 되어 있는 것
- 사람 수와 중복을 나눠 쌓은 막대, 각주에 "GA4는 IP 미제공" 명시 — 정의가 정직하다.
- 네이버·다음 검색어를 리퍼러에서 직접 뽑고, 구글은 서치 콘솔 검색어를 "구글 추정"으로 구분 표기.
- 일부 쿼리가 실패해도 보고서가 만들어지고, 실패 내용을 보고서 하단에 빨간 글씨로 남긴다.
- 서치 콘솔 지연(2~3일)을 코드에서 처리하고 문구로 알린다.

### 바로 고칠 것 (우선순위 순)
1. **'누른 사람' 합산 과대 계산 수정** — `clickersSection()` 의 `sum()` 이 채널·소스·검색어별로 `totalUsers` 를 더한다. 같은 사람이 두 글·두 버튼을 누르면 2명이 된다. 글별 표(`postsSection` 의 `p.clickers += r.m[1]`)도 `linkId` 행(top/mid/end/pop)별 사용자를 더해 같은 문제가 있다.
   - 바꿀 곳: `collect()` 에 `ga(start,end,["sessionDefaultChannelGroup"],["eventCount","totalUsers"],F.cta)` 와 `["linkId"]` 대신 `post_slug` 맞춤 측정기준 기준 쿼리를 추가해 사람 수를 직접 받고, 합산 값은 "누른 횟수"만 쓰기. 맞춤 측정기준 등록 전에는 열 이름을 "누른 사람(행 합산, 중복 가능)"으로 바꾸기.
   - 기대 효과: 사람 기준 클릭률이 부풀려지지 않는다. 확인: 상단 KPI의 '누른 사람'(차원 없는 쿼리)과 채널 합계를 비교해 차이가 0이 아니면 과대 계산 존재.
2. **일간 '어제' 잠정치 표기 + 그제 확정치 재표시** — 08:13에 만든 어제 숫자는 처리 중일 수 있다. `daily()` 의 KPI 카드 제목을 "어제(잠정)"로, `d0`(그제)는 "그제(확정)"로 표기하고, 표에 "다음 날 바뀔 수 있음" 각주 추가. 확인: 1주일간 같은 날짜의 일간 숫자를 다음 날 보고서와 비교해 차이 크기를 기록.
3. **작은 표본 % 표시 억제** — `delta()` 가 2→3도 "▲ 50%"로 그린다. 두 값 중 작은 쪽이 20 미만이면 "2회 → 3회"로만 쓰도록 바꾸고, `kpis()` 클릭률 카드에 Wilson 95% 구간을 작게 표기. 확인: 다음 보고서에서 클릭 수 한 자릿수 날짜에 %가 사라졌는지.
4. **서치 콘솔 행 제한 확대** — `gsc()` 의 `rowLimit: 100` → 1000, 페이지 합계는 page 단독 쿼리로. 확인: 보고서 '구글 검색어' 표의 글별 클릭 합계가 서치 콘솔 화면의 페이지별 클릭과 맞는지.
5. **팝업 성과 넣기** — `popup_view`·`popup_click` 을 글별 표에 추가(노출 대비 클릭률). 결정기록상 유료 광고 유입에는 팝업이 안 뜨므로, 팝업률은 비광고 세션 기준이라고 각주.
6. **맞춤 측정기준 등록 요청(대표 작업)** — `post_slug`, `button_position`, `entry_source`, `entry_page`, `cta_type`, (실험 시) `variant`. 등록 시점부터 쌓이므로 빠를수록 좋다.
7. **내부 트래픽 필터** — 대표·팀 IP를 GA4 내부 트래픽으로 정의(저장소에는 기록하지 않음), 테스트 모드 1주 후 활성.

### 하지 말아야 할 것
- 개인을 식별하려는 시도(IP·지문 수집, 사용자별 추적 보고)는 하지 않는다.
- 행 합산 사용자 수를 "고유 사용자"라고 부르지 않는다.
- 표본이 작은 실험을 "효과 있음"으로 보고하지 않는다. 결과가 불확실하면 그렇게 쓴다.
- 구매·수수료를 GA4 클릭으로 추정해 말하지 않는다. 실제 구매는 네이버 커넥트 관리 화면 숫자만 인용.
- 보고서 저장소(공개)에 서비스 계정 키·IP·이메일을 남기지 않는다(결정기록 보안).
- 대표가 거절한 예약 작업(워크플로)을 임의로 지우거나 끄지 않는다.

1. 오늘 `cta-report` 커밋이 08:13~08:20 사이에 생겼는가, `today.json` 의 `errors` 가 비었는가.

6. 참여 시간 0초 세션이 특정 소스·도시에 몰리지 않았는가(봇 의심).

8. 보고서 그림에서 0 기준 축·단위·기간 표기가 맞는가(템플릿 변경 시).
9. 진행 중인 실험이 있으면 사전 등록한 종료일 전엔 판정하지 않았는가.
10. 광고 집행 중이면 광고 세션(gclid·n_media 등) 클릭을 광고 담당에게 분리 전달했는가.
